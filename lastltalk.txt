how is this case handled in real-world saap-saas applications?

In real-world SaaS, this is usually handled as master reference data governance, not ad-hoc UI entry.

Typical pattern:

countries is a system-owned global master (ISO-3166 based), not tenant-created.
Updates come via controlled migrations or reference-data sync jobs, not manual DB edits in prod.
Tenants get a separate config layer like tenant_country_settings:
enabled/disabled countries
tenant defaults
tax/localization flags
APIs validate countryIso2 against master and return explicit errors if missing.
Rows are usually never hard-deleted; they use is_active + effective dates for safety.
Changes are audited (who, when, before/after) and go through release/change control.
UI normally offers:
searchable dropdown from master
clear “country not available” support/request path
no free-typing in critical flows (or free-typing only with strict validation)
For SaaP specifically, best-practice direction is:

keep countries centrally managed
add new countries via migration/reference seed pipeline
use RBAC/scope to control visibility per tenant, not separate country tables per tenant.

isn't it good practice to add them thro ui ?

For core countries master data, tenant-facing UI add/edit is usually not best practice.

Better pattern:

Keep countries as platform-controlled reference data (ISO-based).
Add/update through controlled admin process (migration or internal backoffice UI), with audit and validation.
Let tenant UI only choose/filter countries, not create new country codes.
Using UI can still be good if it is an internal platform-admin UI with safeguards:

unique iso2/iso3 checks
currency existence checks
audit log + approver flow
soft-delete (is_active) instead of hard delete
prevent changing codes once referenced
So: UI is good for governance workflows, but not for unrestricted tenant self-service creation of canonical countries.
